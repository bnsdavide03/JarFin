\section{Visione del prodotto}

\subsection{Ispirazione e contesto}

L'idea alla base del sistema \textit{JarFin} trae ispirazione dal paradigma degli assistenti intelligenti proattivi, resi popolari in ambito cinematografico da sistemi come J.A.R.V.I.S. (\textit{Just A Rather Very Intelligent System}). In tale contesto ideale, l'assistente è in grado di comprendere richieste espresse in linguaggio naturale e di eseguire operazioni complesse in modo autonomo, riducendo drasticamente il carico cognitivo dell'utente.

Nel mondo reale, tuttavia, la gestione delle finanze personali rappresenta un'attività spesso inefficiente e frammentata. Gli utenti sono costretti a utilizzare molteplici applicazioni bancarie, inserire manualmente dati in fogli di calcolo e navigare interfacce complesse (WIMP) per ottenere informazioni basilari sul proprio stato finanziario.
Questa modalità operativa introduce un'elevata "frizione", aumentando il rischio di errori di trascrizione e riducendo la frequenza con cui gli utenti monitorano le proprie finanze.

\newpage
\subsection{Obiettivi del sistema}

JarFin si propone di colmare questo divario introducendo un assistente finanziario intelligente in grado di:
\begin{itemize}
    \item comprendere comandi espressi in linguaggio naturale (NLU);
    \item trasformare input non strutturati (es. "Pizza 20 euro") in operazioni finanziarie formalmente definite;
    \item centralizzare la gestione delle transazioni finanziarie in un unico hub;
    \item fornire funzionalità avanzate di analisi e reporting automatico;
    \item garantire un'architettura scalabile, modulare ed estendibile tramite microservizi.
\end{itemize}

\section{Strategia di modellazione architetturale}

Per gestire la complessità di un sistema distribuito, è stato adottato il modello \textbf{UML 4+1 View Model}. Questo approccio consente di descrivere l'architettura attraverso cinque viste concorrenti:
\begin{itemize}
    \item \textbf{Vista Scenari}: descrive le interazioni utente-sistema (Casi d'Uso).
    \item \textbf{Vista Logica}: descrive la struttura statica e il dominio (Classi).
    \item \textbf{Vista di Sviluppo}: descrive l'organizzazione dei moduli software (Componenti).
    \item \textbf{Vista di Processo}: descrive il comportamento dinamico e i flussi (Sequenza).
    \item \textbf{Vista Fisica}: descrive il deployment sull'infrastruttura (Deployment).
\end{itemize}

\subsection{Attori}
Il diagramma identifica due tipologie di attori:
\begin{itemize}
    \item \textbf{Utente}: attore primario che interagisce con l'interfaccia web per la gestione delle proprie finanze.
    \item \textbf{Sistemi esterni}: attori secondari necessari al funzionamento del backend:
          \begin{itemize}
              \item \textbf{Cloud Speech-to-Text}: servizio invocato per la trascrizione dei comandi vocali;
              \item \textbf{Database}: sistema responsabile della persistenza fisica di tutte le entità (utenti, transazioni, categorie).
          \end{itemize}
\end{itemize}

\subsection{Descrizione dei Casi d'Uso}

Le funzionalità sono state raggruppate in tre macro-aree logiche per facilitarne la lettura e l'implementazione.

\subsubsection{Gestione Accesso}
Include le operazioni di sicurezza e identificazione, necessarie per garantire che i dati finanziari siano accessibili solo al proprietario.
\begin{itemize}
    \item \textbf{Registrazione, Login e Logout}: casi d'uso distinti che gestiscono il ciclo di vita della sessione utente.
\end{itemize}

\subsubsection{Gestione Transazioni}
Rappresenta il nucleo operativo dell'applicazione (\textit{Core Domain}).
\begin{itemize}
    \item \textbf{Registrare Transazione}: permette l'inserimento di una nuova spesa o entrata.
          \begin{itemize}
              \item \textit{Inclusione («include»)}: include obbligatoriamente il caso d'uso \textbf{"Conversione NL ad Azione"}, poiché ogni input (testuale o vocale) deve essere processato dal parser NLU per estrarre i dati strutturati.
              \item \textit{Estensione («extend»)}: è esteso da \textbf{"Conversione STT"} se la condizione \texttt{input == vocale} è soddisfatta.
          \end{itemize}
    \item \textbf{Gestire Transazioni}: permette la modifica o l'eliminazione di movimenti esistenti.
          \begin{itemize}
              \item Anche questo caso d'uso include la logica di parsing NLU ed è esteso dalla conversione vocale, permettendo all'utente di modificare i dati tramite comandi vocali.
          \end{itemize}
\end{itemize}

\subsubsection{Analisi e Configurazione}
Riguarda le funzionalità di monitoraggio e organizzazione dei dati.
\begin{itemize}
    \item \textbf{Consultare Stato Finanziario}: visualizzazione immediata del saldo attuale.
    \item \textbf{Gestire Fondi e Budget}: definizione dei limiti di spesa mensili.
    \item \textbf{Gestire Categorie}: permette all'utente di creare, modificare o eliminare le categorie di spesa personalizzate (es. "Svago", "Casa").
    \item \textbf{Visualizzare Report e Stime}: generazione di grafici e proiezioni future basate sullo storico delle transazioni.
\end{itemize}

\subsection{Shared Kernel e Modello di Dominio}
La parte sinistra del diagramma definisce le entità core, condivise concettualmente tra i moduli:
\begin{itemize}
    \item \textbf{\texttt{User}}: rappresenta l'utente del sistema. È la radice dell'aggregato e possiede una relazione uno-a-uno con \texttt{Account}.
    \item \textbf{\texttt{Account}}: rappresenta il portafoglio digitale. Mantiene la lista delle transazioni associate.
    \item \textbf{\texttt{Transaction}}: l'entità centrale, caratterizzata da attributi come importo, data e descrizione. È associata a una \textbf{\texttt{Category}} (es. "Cibo", "Casa") per permettere analisi tematiche.
\end{itemize}

\subsection{Microservizio Accounting}
Situato nella parte inferiore, implementa il classico pattern a tre livelli per la gestione dei dati finanziari:
\begin{itemize}
    \item \textbf{\texttt{TransactionController}}: espone gli endpoint REST per le operazioni CRUD.
    \item \textbf{\texttt{TransactionService}}: incapsula la logica di business e valida i dati in ingresso.
    \item \textbf{\texttt{TransactionRepository}}: interfaccia che estende \textit{Spring Data JPA}, gestendo l'accesso diretto al database.
\end{itemize}

\subsection{Microservizio NLU (Natural Language Understanding)}
Il modulo in alto a destra gestisce l'interpretazione dei comandi. La sua struttura evidenzia la separazione tra ricezione del comando ed elaborazione:
\begin{itemize}
    \item \textbf{\texttt{NLUController}}: riceve l'input (testuale o vocale) dall'API Gateway.
    \item \textbf{\texttt{NLUService}}: coordina il processo di analisi.
    \item \textbf{\texttt{ParserNLU}}: il componente core che esegue il pattern matching per estrarre intenti e parametri dalla stringa di testo.
    \item \textbf{\texttt{SpeechToTextService}}: interfaccia che astrae la comunicazione con il servizio cloud esterno per la trascrizione vocale, garantendo che il resto del sistema rimanga agnostico rispetto alla tecnologia STT scelta.
\end{itemize}

\subsection{Microservizio Analytics}
Visibile in basso a destra, è dedicato all'elaborazione statistica:
\begin{itemize}
    \item \textbf{\texttt{AnalyticsController}}: espone gli endpoint per la richiesta di report.
    \item \textbf{\texttt{DataAggregator}}: classe specializzata che elabora collezioni di transazioni per calcolare totali, medie e proiezioni, restituendo oggetti di tipo \textbf{\texttt{Report}}.
\end{itemize}

\subsection{Orchestrazione}
Al centro del diagramma, la classe \textbf{\texttt{APIGateway}} agisce come facciata (\textit{Facade Pattern}) verso il client. Le linee tratteggiate indicano che il Gateway non possiede le logiche di business, ma dipende dai Controller dei singoli microservizi per inoltrare le richieste e aggregare le risposte.

Questa vista evidenzia la struttura a livelli (\textit{Layered Architecture}), separando nettamente la presentazione, la logica di business e la persistenza dei dati.

    \caption{Diagramma dei componenti: architettura a livelli e interfacce esposte.}
    \label{fig:components}

\subsection{Client Layer (Presentation)}
Il livello superiore rappresenta il frontend dell'applicazione.
\begin{itemize}
    \item \textbf{Componente GUI}: Gestisce il rendering dell'interfaccia grafica.
    \item \textbf{Interfacce}: Il componente implementa l'interfaccia \texttt{UserInterface}, che espone i metodi \texttt{inputCommand()} e \texttt{displayReport()}.
    \item \textbf{Porte}: La comunicazione verso l'esterno avviene tramite la porta \textbf{\texttt{GUIPORT [1]}}, che funge da connettore verso l'\textit{API Gateway}.
\end{itemize}

\subsection{Application Layer (Business Logic)}
Il nucleo del sistema è accessibile tramite la porta di ingresso \textbf{\texttt{APPORT [1]}} e comprende tre microservizi:
\begin{itemize}
    \item \textbf{NLU Service}: Espone l'interfaccia \texttt{NLUInterface} con il metodo \texttt{parseCommand()}. Al suo interno incapsula l'artefatto \texttt{ParserNLU.java} per l'analisi semantica.
    \item \textbf{Accounting Service}: Gestisce la contabilità tramite \texttt{AccountingInterface}, offrendo i metodi \texttt{addTransaction()} e \texttt{getBalance()}.
    \item \textbf{Analytics Service}: Espone \texttt{AnalyticsInterface} e utilizza l'artefatto \texttt{DataAggregator.java} per calcolare le statistiche (\texttt{getStatistics()}).
\end{itemize}
Il layer comunica con il livello dati sottostante attraverso la porta di uscita \textbf{\texttt{APPORTDB [1]}}.

\subsection{Data Layer (Persistence)}
Il livello inferiore riceve le richieste sulla porta \textbf{\texttt{DBPORT [1]}}.
\begin{itemize}
    \item \textbf{Componente Database}: Gestisce l'archiviazione fisica (PostgreSQL).
    \item \textbf{\texttt{DBInterface}}: Astrae le operazioni di basso livello quali \texttt{save()} e \texttt{query()}, garantendo il disaccoppiamento tra logica applicativa e storage.
\end{itemize}

\subsection{Dipendenze Esterne}
\begin{itemize}
    \item \textbf{STT Service}: Componente esterno collegato tramite una relazione di dipendenza \texttt{«use»}. È invocato dal servizio NLU per la trascrizione dei comandi vocali.
\end{itemize}

Il diagramma è strutturato in due macro-fasi logiche: la gestione dell'identità utente (parte superiore) e l'esecuzione dei comandi operativi (parte inferiore).

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{../Iterazione_0/images/sequence_diagram.png}
    \caption{Diagramma di sequenza: autenticazione, gestione comandi e routing.}
    \label{fig:sequence}
\end{figure}

\subsection{Fase 1: Gestione Accesso e Autenticazione}
La parte iniziale del diagramma modella il ciclo di vita della sessione utente:
\begin{enumerate}
    \item \textbf{Registrazione}: L'utente non registrato invia una richiesta \texttt{POST /auth/register}. L'API Gateway inoltra la richiesta al servizio di autenticazione, che gestisce la persistenza dei dati utente.
    \item \textbf{Login}: L'utente registrato invia le credenziali tramite \texttt{POST /auth/login}. Il sistema recupera l'hash della password (\texttt{SELECT Password Hash}) e, in caso di validazione positiva, restituisce un \textbf{Token di Sessione} necessario per le chiamate successive.
\end{enumerate}

\subsection{Fase 2: Elaborazione dei Comandi}
Una volta autenticato, l'utente invia comandi (Request + TOKEN). Il flusso segue questi passaggi:

\begin{enumerate}
    \item \textbf{Gestione Input Vocale (Frammento \texttt{opt})}:
          Se la condizione \texttt{[Input è vocale]} è vera, il Gateway invia il flusso audio al servizio esterno \textit{Cloud STT} e attende la trascrizione testuale.

    \item \textbf{Analisi Semantica}:
          Il testo (originario o trascritto) viene inviato al \textbf{NLU Service} (\texttt{POST /parse}). Il servizio restituisce un JSON contenente l'intento identificato e i dati estratti.

    \item \textbf{Routing e Logica di Business (Frammento \texttt{alt})}:
          Sulla base dell'intento ricevuto, il Gateway instrada la richiesta verso il microservizio competente:

          \begin{itemize}
              \item \textbf{Ramo Scrittura (Accounting)}: Se l'intento riguarda modifiche (es. "Spese", "Budget"), viene invocato l'\textbf{Accounting Service}.
                    Un ulteriore frammento condizionale distingue tra:
                    \begin{itemize}
                        \item \textit{Nuova Entità}: Esegue una \texttt{INSERT into table} sul Database.
                        \item \textit{Modifica}: Esegue una \texttt{UPDATE table} sul Database.
                    \end{itemize}

              \item \textbf{Ramo Lettura (Analytics)}: Se l'intento è di analisi (es. "Report"), viene invocato l'\textbf{Analytics Service} (\texttt{GET /stats}), che interroga il Database (\texttt{SELECT Aggregazione}) per ottenere i dati grezzi ed elaborarli.
          \end{itemize}

    \item \textbf{Risposta}:
          L'esito dell'operazione (conferma o report JSON) viene restituito a ritroso fino alla \textit{Client Application}, che fornisce il feedback finale all'utente.
\end{enumerate}

\subsection{Architettura dei Nodi e Ambienti}
Il sistema è distribuito su quattro entità computazionali distinte, configurate come segue:

\begin{itemize}
    \item \textbf{User Device (Client)}: Rappresenta il dispositivo dell'utente (PC, smartphone). Ospita l'ambiente di esecuzione \textit{Web Browser}, all'interno del quale viene caricato l'artefatto \textbf{\texttt{JarFin Web UI}}. L'approccio \textit{Zero-Install} delega il rendering interamente al browser.

    \item \textbf{Cloud Server (Application Host)}: Il nodo server che ospita la logica di business. È configurato come un ambiente di orchestrazione container (Docker Host), suddiviso in tre ambienti di esecuzione isolati per massimizzare l'indipendenza dei servizi:
          \begin{itemize}
              \item \textbf{Container NLU}: esegue l'artefatto \texttt{ParserNLU.jar}.
              \item \textbf{Container Accounting}: esegue l'artefatto \texttt{AccountingService.jar}.
              \item \textbf{Container Analytics}: esegue l'artefatto \texttt{AnalyticsService.jar}.
          \end{itemize}

    \item \textbf{Database Server}: Nodo dedicato alla persistenza che ospita il DBMS \textbf{PostgreSQL}. La sua separazione fisica dal server applicativo è una scelta architetturale critica per garantire sicurezza dei dati e performance di I/O dedicate.

    \item \textbf{External STT Service}: Nodo esterno al perimetro del sistema (Third-Party Service), che fornisce le funzionalità di Speech-to-Text on-demand.
\end{itemize}

\subsection{Protocolli di Comunicazione}
Le connessioni tra i nodi avvengono tramite canali sicuri e standardizzati:

\begin{itemize}
    \item \textbf{User Device $\xrightarrow{HTTPS}$ Cloud Server}: La comunicazione Client-Server è cifrata tramite protocollo \textbf{HTTPS}. Le richieste vengono intercettate e instradate dall'\textit{API Gateway} verso i container specifici, nascondendo la complessità interna al client.

    \item \textbf{Cloud Server $\xrightarrow{JDBC}$ Database Server}: I microservizi accedono ai dati persistenti utilizzando il protocollo standard \textbf{JDBC} (Java Database Connectivity) su TCP/IP, demandando al DBMS PostgreSQL la garanzia delle proprietà ACID.

    \item \textbf{Cloud Server $\xrightarrow{HTTPS/JSON}$ External STT}: Il servizio NLU invia i flussi audio al servizio esterno tramite chiamate REST su \textbf{HTTPS}, ricevendo in risposta la trascrizione in formato \textbf{JSON}.
\end{itemize}
